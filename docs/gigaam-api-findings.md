## 1. Таймкоды — ЕСТЬ, пословные ✅ (блокирующий вопрос закрыт)

`transcribe()` и `transcribe_longform()` принимают флаг **`word_timestamps: bool = False`**
и при `True` возвращают **пословные** таймкоды. Это первоклассный API, не хак:

- Датаклассы: `Word{text, start, end}` (:59), `TranscriptionResult{text, words}` (:66),
  `Segment{text, start, end, words}` (:75), `LongformTranscriptionResult{segments}`
  (:83, свойства `.words` :87, `.has_word_timestamps` :96).
- Механика: CTC greedy decode возвращает `(text, token_ids, token_frames)` —
  индексы фреймов эмиссии каждого токена (`CTCGreedyDecoding.decode`, :998-1037,
  контракт в докстринге :1004-1007). Далее `compute_frame_shift` (:619) считает
  секунды-на-фрейм динамически (`samples / 16000 / seq_len`; субдискретизация 4×
  на hop 10 мс → ~40 мс/фрейм), а `frames_to_words` (:624-663) группирует токены
  в слова по границам sentencepiece-`▁`/пробела: `start = first_frame*shift`,
  `end = (last_frame+1)*shift`.
- В longform-режиме тайминги слов приводятся к **глобальной шкале записи**
  автоматически: `Word(start=round(w.start + seg_start, 3), ...)` (:2020-2027).
  Границы сегментов тоже глобальные (:2013).
- Гранулярность = 1 фрейм ≈ 40 мс. Для нашего контракта: `int(round(w.start * 1000))`.
- Сырые CTC-логиты при желании доступны: `head(encoder_output=...)` → log_probs
  (:1009), но не нужны — слова уже готовы.

Точность таймкодов — это эмиссионные позиции CTC (токен «выстреливает» ближе к
концу звучания символа); для якорей реплик этого достаточно, но `end` последнего
слова сегмента может слегка недотягивать до фактического конца речи.

## 2. Язык — параметра НЕТ, автоопределения НЕТ

- Ни `transcribe*()`, ни конфиг не принимают язык. `grep -i lang` по всему файлу —
  ноль вхождений. Модель — **посимвольный CTC над единым алфавитом из 70 символов**
  (config.json → `decoding.vocabulary`): пробел, апостроф, латиница `a-z`,
  русская кириллица (с `ё`) и центральноазиатские буквы `і ғ қ ң ү ұ һ ә ө`.
- Следствие для смешанной ru/uz речи в одном предложении: модель просто эмитит
  символы того алфавита, на котором прозвучало слово (узбекская латиница и русская
  кириллица сосуществуют в одной строке). Ничего не переключается и не ломается —
  но и метки языка нет.
- Для контракта: `detected_language = None` всегда. Если язык нужен downstream —
  определять на нашей стороне по алфавиту слова (латиница+`'` ≈ uz, кириллица ≈ ru/kk/ky)
  — это пост-обработка, не функция модели.
- `confidence`: greedy decode вероятностей наружу не отдаёт (:998-1037) → в
  контракте всегда `None` (поле оставляем на будущее).

## 3. Варианты: ctc vs large_ctc

| | `ctc` | `large_ctc` |
|---|---|---|
| Параметры | 220M (16 слоёв, d=768) | 600M (24 слоя, d=1024) |
| Веса fp32 | 883 МБ | 2 342 МБ |
| WER uz (CV / FLEURS / internal) | 11.3 / 10.0 / 13.8 | **9.2 / 7.3 / 12.7** |
| WER ru (CV / FLEURS / internal) | 7.1 / 4.4 / 7.6 | **5.1 / 3.0 / 6.0** |

(Для сравнения Whisper large v3 на узбекском: WER 105–120 — фактически не работает.)

**Рекомендация: `large_ctc`** — на целевом узбекском на ~20 % меньше ошибок, а по
VRAM всё равно помещается на самую дешёвую карту (см. §6). `ssl`/`large_ssl` —
бэкбоны без CTC-головы, для инференса не подходят (подтверждено конфигами: у них
нет `head`/`decoding`).

## 4. Длинное аудио — нарезка ВСТРОЕНА, но с операционной ловушкой

- `transcribe()` жёстко отказывает файлам длиннее **25 с**: `LONGFORM_THRESHOLD =
  25 * SAMPLE_RATE` (:1792), проверка :1913 → `ValueError("Too long wav file...")`.
  Для встреч всегда используем `transcribe_longform()`.
- `transcribe_longform` (:1974-2037): VAD-сегментация → чанки **15–22 с**
  (жёсткий предел 30 с, сверхдлинные сегменты режутся поровну, :740-800) →
  батч-инференс через DataLoader (`fr_batch_size=16`) → сегменты с глобальными
  границами и глобальными пословными таймингами. Максимум длины записи не
  ограничен ничем, кроме памяти под load_audio (float32 в RAM: час ≈ 230 МБ — ок).
- **Ловушка**: VAD — это `pyannote/segmentation-3.0` (:718, :740), модель **gated**
  на HF. Нужно: (а) один раз принять условия на её странице, (б) прокинуть
  `HF_TOKEN` в контейнер (:688-693 — без токена и локального кэша падает с
  `RuntimeError`), (в) установить `pyannote.audio` (импортируется лениво, :697).
  После первого скачивания кэшируется (у нас — на Modal Volume), токен нужен
  только для первого прогрева.
- Перехлёст окон **не нужен**: нарезка идёт по границам тишины (VAD), а не по
  глухим таймерам — дедупликации на стыках нет и не требуется. Собственный
  `chunking.py` не нужен; оставляем его в структуре только если решим уйти от
  gated-pyannote (тогда silero-vad + `transcribe(word_timestamps=True)` по чанкам
  со смещением — план Б, ~50 строк).

## 5. Формат входа

- **Оба `transcribe*()` принимают ТОЛЬКО путь к файлу** (`wav_file: str`).
  numpy/Tensor принимает лишь внутренний `AudioDataset._load_audio` (:567-580),
  наружу это не торчит.
- Декодирование пути: **ffmpeg CLI сабпроцессом** (`load_audio`, :118-146:
  `ffmpeg -nostdin -i <path> -f s16le -ac 1 -ar 16000 -`) → float32 [-1;1].
  Значит: (а) в образе обязателен ffmpeg, (б) любой формат на входе модель
  переварит сама, но валидацию мы всё равно делаем ДО неё через `soundfile`
  (наш вход — уже нормализованный 16 кГц mono WAV PCM; ffmpeg для него —
  прозрачный passthrough), (в) байты из presigned URL пишем во временный файл.
- VAD-пайплайн longform тоже читает файл по пути (:749 `pipeline(wav_file)`).
- На GPU форвард автокастится в fp16 (:1814-1816), на CPU — fp32.

## 6. Размер весов и VRAM → GPU

- `large_ctc`: 2.34 ГБ fp32 весов + активации чанков ≤30 с (батч 16) + мелкая
  pyannote-сегментация ≈ **< 6 ГБ VRAM пиково**. `ctc`: < 3 ГБ.
- **L4 (24 ГБ, ~$0.80/ч на Modal) — с большим запасом**; влез бы и T4. Дорогая
  карта не нужна, выбор L4 подтверждается.
- Холодный старт (оценка, уточним замером при деплое): контейнер + загрузка
  2.3 ГБ весов с Volume + pyannote ≈ 30–60 с. Замер — в критериях приёмки.

## 7. Зависимости образа (из импортов кода, :19-41)

`torch==2.10.*`, `torchaudio==2.10.*`, `transformers==5.*` (рекомендация README),
`hydra-core`, `omegaconf`, `soundfile`, `sentencepiece` (импортируется на верхнем
уровне даже для char-CTC), `pyannote.audio` (longform), `huggingface_hub`,
системный `ffmpeg`. **Несовместимо с образом GigaChat3.1-Audio** (тому нужен
`transformers==4.57.*`) — отдельный контейнер обязателен, что и требовалось.

## 8. Ответ на вызов из README (для справки)

```python
model = AutoModel.from_pretrained(
    "ai-sage/GigaAM-Multilingual",
    revision="3905cd51c3ed4e88c8edf33f3302969ba480a327",  # large_ctc, пин по SHA
    trust_remote_code=True,
)
res = model.transcribe_longform("meeting.wav", word_timestamps=True)
# res.segments[i]: Segment{text, start, end, words=[Word{text, start, end}, ...]}
# все времена — float-секунды в глобальной шкале записи; наш контракт переводит в int-мс
```

## Вердикт

Блокирующих проблем нет: **пословные таймкоды есть нативно**, длинное аудио
модель режет сама с глобальной шкалой времени. Единственное операционное
требование — gated `pyannote/segmentation-3.0`: принять условия на HF и завести
`HF_TOKEN` как Modal Secret (нужен один раз до прогрева кэша).
