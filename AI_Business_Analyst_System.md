# AI Business Analyst — System Context (for Claude Code)

> Контекстный брифинг для AI-агента разработки. Описывает **будущую систему**
> структурированного приёма и ведения бизнес-запросов между Product Owner,
> бизнес-менеджерами и разработкой. Источник истины — этот файл + связанные
> документы (PRD, План по фазам, Анализ шаблонов).
>
> Чтобы Claude Code загружал контекст автоматически, можно переименовать файл в `CLAUDE.md`
> в корне репозитория.

---

## 1. Что это и зачем

Платформа: **Private Enterprise AI Platform BuildX** (Beeline Uzbekistan).
Стадия: **Pre-MVP / Discovery**. Горизонт: **12 месяцев**.

**Проблема.** Бизнес приходит к разработке с размытыми, вербальными запросами.
Нет структуры входящих, «рваные» сроки, нет плановой фиксации требований и нет
сквозной аналитики проектов — даже у самих бизнес-аналитиков.

**Решение.** Система, которая превращает устный размытый запрос в
структурированный, прослеживаемый и измеримый артефакт: шаблоны → управляемый
workflow → трекинг тикетов → фиксация «было/стало» → ТЗ → двойная приёмка →
сквозная аналитика.

**Цель для разработки.** Построить продукт, который реализует эту цепочку с
единым ядром метаданных и сквозной трассируемостью требований.

## 2. Цели и метрики успеха (MVP)

| Цель | Метрика | Целевое значение |
|---|---|---|
| Структурность входящих | Доля запросов через шаблон (не вербально) | ≥ 80% |
| Полнота требований | Доля тикетов в работу без возврата на доработку | ≥ 70% |
| Прогнозируемость сроков | Отклонение факт/план по срокам | ≤ 20% |
| Сквозная аналитика | Покрытие тикетов в системе | 100% |
| Подтверждённая польза | Доля закрытых тикетов с зафиксированным value | ≥ 60% |

Метрики — ориентировочные, уточняются на discovery.

---

## 3. Пользователи и модель доступа (tenants)

Модель: **открытый доступ + обязательный роутинг**. Тикет может завести любой
сотрудник, но он проходит триаж до начала работ.

| Роль | Кто | Права / ответственность |
|---|---|---|
| Заявитель | Любой сотрудник | Создаёт тикет (шаблон/свободная форма), отслеживает статус |
| Триаж / BA | Бизнес-аналитик | Проверка полноты, маршрутизация, оформление ТЗ, ведение по workflow |
| Бизнес-заказчик | Инициатор потребности | Согласует требования, подтверждает ценность на приёмке (value-гейт) |
| Исполнитель | Разработка | Принимает ТЗ, оценивает сроки, выполняет, фиксирует «было/стало» |
| Согласующий | Руководитель направления | Приоритизация и одобрение крупных инициатив (M+) |

---

## 4. Жизненный цикл заявки (workflow)

Статусная модель. Переход в работу — только после согласованного ТЗ;
закрытие — только после двойной приёмки.

```
Создан → Триаж → ТЗ/Согласование → В работе → Фиксация изменений → Приёмка → Закрыт
                                                                          ↘ Отклонён
```

| Статус | Что происходит | Ответственный |
|---|---|---|
| 1. Создан | Подача запроса (шаблон/свободная форма) | Заявитель |
| 2. Триаж | Проверка полноты, дедупликация, маршрутизация | BA / триаж |
| 3. ТЗ / Согласование | Оформление ТЗ, согласование, протокол | BA + бизнес |
| 4. В работе | Оценка сроков и выполнение | Исполнитель |
| 5. Фиксация изменений | Запись «было/стало» и результатов | Исполнитель + BA |
| 6. Приёмка | Двойной гейт: BA (формально) + бизнес (value) | BA + бизнес |
| 7. Закрыт | Закрыт успешно → данные в аналитику | BA |
| ✕ Отклонён | Дубль / нерелевантно / не обосновано | BA / триаж |

**Определение успешно закрытого тикета (двойной гейт):**
1. **Формальный (DoD), решает BA** — выполнены AC из ТЗ, зафиксировано «было/стало», оформлен протокол, нет открытых P0/P1.
2. **Ценностный (value), решает бизнес-заказчик** — результат решает исходную задачу и приносит заявленную пользу.

## 5. Система шаблонов (гибрид)

Каталог шаблонов под частые кейсы + свободная форма для нетиповых запросов
(с обязательным минимальным ядром). База шаблонов формируется из примеров в Confluence.

| Тип формы входа | Назначение | Опорный шаблон документации |
|---|---|---|
| Запрос на разработку фичи | Новая функциональность с гипотезой ценности | BRD → SRS / Use Case |
| Доработка / изменение логики | Изменение поведения системы | Change Specification |
| Исправление / дефект | Проблема: ожидаемое vs фактическое | Change Specification (мин.) |
| Интеграция / данные | Подключение источника, обмен, выгрузки | SRS (интеграции) + Change Spec |
| Аналитический запрос | Отчёт, дашборд, исследование | Change Specification (выходные данные) |
| Свободная форма | Нетиповой запрос | Ядро метаданных + обязательные поля |

**Обязательные поля любой формы:** проблема/потребность, ожидаемый результат и
измеримый эффект, затронутые системы/стейкхолдеры, срочность/срок, критерии приёмки.

## 6. Унифицированная структура требований

> Это ядро доменной модели. Реализовать как сущности и связи в БД/бэкенде.

### 6.1. Единое ядро метаданных (шапка любого артефакта)

`ID`, `Название`, `Тип` (BRD/SRS/UseCase/ChangeSpec), `Автор`, `Дата`, `Версия`,
`Статус` (Черновик/На согласовании/Утверждён/В работе/Закрыт), `Приоритет`
(ценность·срочность·риск), `Источник/Заказчик`, `Связи` (трассировочные ссылки).

### 6.2. Схема идентификаторов и трассируемость

**Цепочка:** `BG → BR → (UC / US) → FR / NFR → AC → TC`
Каждый нижний уровень ссылается на верхний — так видно, что всё работает на бизнес-цель.

| Уровень | Префикс | Описывает | Где живёт |
|---|---|---|---|
| Бизнес-цель | `BG-XX` | Измеримая цель / KPI | BRD |
| Бизнес-требование | `BR-XX` | Что нужно на бизнес-уровне | BRD |
| Бизнес-правило | `RULE-XX` | Политика/правило домена | SRS / Use Case |
| Сценарий | `UC-XX` / `US-XX` | Поведение пользователя и системы | Use Case / SRS |
| Функц. требование | `FR-XX` | Конкретная функция | SRS / Change Spec |
| Нефункц. требование | `NFR-XX` | Качество, ограничения | SRS |
| Критерий приёмки | `AC-XX` | Проверяемый признак готовности | Все |
| Тест-кейс | `TC-XX` | Проверка требования | SRS / план тестов |

> **ВАЖНО (исправленная коллизия):** префикс `BR` = только **бизнес-требование**.
> Бизнес-правило — отдельный префикс `RULE`. В старых шаблонах `BR` ошибочно
> использовался для обоих понятий.

### 6.3. Обязательные измеримые поля (во всех формах входа)

- **Цель бизнеса** — зачем (привязка к `BG`).
- **Метрика успеха** — число, не абстракция.
- **AS-IS / TO-BE** — что сейчас и что должно стать.
- **Acceptance Criteria** — проверяемые признаки готовности.

Принцип гайдлайна: ответы чёткие и измеримые, без абстрактности; до старта —
проверка на противоречия, точность и скрытую проблему.

### 6.4. Правило выбора шаблона

| Ситуация | Шаблон | Уровень |
|---|---|---|
| Новая идея/боль — нужен бизнес-кейс | BRD | Бизнес |
| Новое приложение / крупная система | SRS (+ BRD) | Система |
| Описать поведение и сценарии | Use Case | Сценарный |
| Мелкая доработка (1–2 изменения) | Change Specification | Задача |
| > 2 изменений или новый модуль | SRS | Система |
| Нетиповой запрос | Свободная форма + ядро | Любой |

---

## 7. Процесс бизнес-анализа (как работает BA — контекст домена)

**Трек А. Новое приложение:**
Clarification → AS-IS → TO-BE → **BRD** → Декомпозиция (FR/NFR, Use Case/US) →
**SRS** → Grooming → Estimation → Приоритизация → DoD → Передача в разработку.

**Трек Б. Доработка существующего:**
Быстрое уточнение → **Impact Analysis** → Декомпозиция (Epic→Feature→Story) →
**Change Specification** (или Use Case) → Детализация JIT (AC, edge cases) →
Grooming → Поддержка разработки.

## 8. Нефункциональные требования и комплаенс

- **RBAC** — права по ролям; разделение зон данных между отделами.
- **Локализация ПДн в РУз**; полные **аудит-логи** действий по тикету.
- **Прослеживаемость** — полная история изменений и согласований.
- **Интеграции в стиле MCP** — Confluence, трекер, источники данных.
- **Человеческий контроль** на юридически значимых решениях (не на AI).

## 11. Глоссарий

- **BA** — бизнес-аналитик. **PO** — Product Owner.
- **BRD** — Business Requirements Document (бизнес-уровень).
- **SRS** — Software Requirements Specification (системный уровень).
- **Use Case** — сценарий поведения пользователя/системы.
- **Change Spec** — спецификация мелкого изменения (1–2 правки).
- **AS-IS / TO-BE** — текущее / целевое состояние процесса.
- **DoD** — Definition of Done. **AC** — Acceptance Criteria.
- **Impact Analysis** — анализ влияния изменения на модули/API/данные.
- **Grooming** — синхронизация требований BA с разработкой.
- **Триаж** — первичная проверка и маршрутизация тикета.

## 13. Подсказки для агента разработки

- Доменное ядро = **тикет** с единым ядром метаданных (раздел 6.1) и **трассируемостью** (6.2).
- Любой результат должен поддерживать сквозную аналитику и фиксацию «было/стало».
- Закрытие тикета = двойной гейт; AC обязательны и проверяемы.
- Соблюдать комплаенс (раздел 8) на уровне архитектуры, не «вдогонку».
- Платформа трекинга ещё не выбрана — избегать жёсткой привязки к конкретному трекеру.
